# Tarot de Delphes

Application web (PWA) de tarot mythologique grec — tirage interactif, lecture personnalisée générée par IA, bibliothèque de symboles, journal.

## Structure
- `index.html` — structure de la page
- `styles.css` — tous les styles (police Cinzel/EB Garamond, thème "divinatoire", animation de chargement en étoiles)
- `app.js` — toute la logique (données des cartes, symboles, tirage, navigation, appel au backend IA)
- `assets/` — illustrations des 22 arcanes majeurs (Le Mat, Bateleur, Papesse, Impératrice, Empereur, Pape, Amoureux, Chariot, Justice, Hermite, Roue de Fortune, Force, Pendu, Arcane sans nom, Tempérance, Diable, Maison-Dieu, Étoile, Lune, Soleil, Jugement, Monde) — collection complète. Illustration progressive des 56 cartes mineures : le jeu d'Épées et le jeu de Bâtons sont désormais complets (10 numérales + 4 figures de cour chacun, `card-epees-*.jpg` et `card-batons-*.jpg`) ; le jeu de Coupes a reçu ses 5 premières numérales (As à 5, `card-coupes-*.jpg`) ; le reste (Coupes 6-10 et figures de cour, Deniers) utilise encore un glyphe emoji ou des pips en attendant son illustration. 4 illustrations (`learn-*.jpg`) pour les cases de l'onglet Apprendre, et 4 illustrations (`suit-*.jpg`) pour les 4 enseignes dans les sous-sections « Figures de cour » et « Cartes numérales ».
- `manifest.json` + `icon.svg` — nécessaires pour l'installation en PWA
- `service-worker.js` — cache offline
- `api/reading.js` — backend serverless (Vercel) qui appelle l'API Anthropic côté serveur
- `api/astral.js` — backend serverless (Vercel) qui calcule un profil astral (thème natal) à partir d'une date/heure/lieu de naissance
- `api/transits.js` — backend serverless (Vercel) qui calcule les positions planétaires du jour, pour l'Horoscope du jour (aucune donnée personnelle reçue)
- `api/portrait.js` — backend serverless (Vercel) qui rédige, une seule fois par profil, un portrait de personnalité (texte suivi) à partir d'un résumé du thème natal
- `api/astral-text.js` — backend serverless (Vercel) qui rédige, une seule fois par profil, une phrase personnalisée pour chaque case du Profil astral (nombre du prénom, chaque planète, l'ascendant, chaque aspect) et explique le choix de la divinité tutélaire
- `api/retrospective.js` — backend serverless (Vercel) qui rédige, une fois par an à l'anniversaire, un bilan de l'année de tirages écoulée à partir d'un résumé agrégé du Journal
- `api/ritual.js` — backend serverless (Vercel) qui rédige, une fois par jour, l'Horoscope du jour affiché à l'accueil : une recommandation unique reliant carte du jour + transits (signes + aspect le plus marqué avec le thème natal) + thème natal fixe (Soleil/Lune/ascendant) + nombre personnel du jour
- `api/comparison-text.js` — backend serverless (Vercel) qui rédige, une seule fois par proche, un texte suivi qui tisse la comparaison de thèmes déjà calculée localement (« Mes proches ») en une lecture fluide adaptée au type de relation
- `api/_lib/astro.js` — briques astronomiques partagées entre `api/astral.js` et `api/transits.js` (longitudes écliptiques, signes, aspects) ; le préfixe `_` évite que Vercel n'en fasse une route
- `package.json` — dépendances `@anthropic-ai/sdk` (`api/reading.js`, `api/portrait.js`, `api/astral-text.js`, `api/retrospective.js`, `api/ritual.js`, `api/comparison-text.js`), `luxon` + `astronomy-engine` (`api/astral.js`, `api/transits.js`)

## Lecture générée par IA — comment ça marche
La fonction `generateAIReading(question, cards, positions)` dans `app.js` envoie `{question, cards, positions, profile?, history?, memory?}` en `POST` vers `/api/reading` — `positions` (les intitulés des positions du tirage choisi, ex. « Défi », « Résultat ») donne à l'IA le sens de chaque carte dans les tirages autres que le tirage général ; `profile`, `history` et `memory` sont trois résumés optionnels de personnalisation (voir « Profil astral », « Journal intelligent » et « Mémoire du Journal » plus bas). Quand un prénom est enregistré, l'IA est aussi invitée à s'adresser à la personne par son prénom une fois dans la lecture, jamais de façon systématique. Cette fonction serverless (`api/reading.js`), agnostique du type de tirage (1 à 12 cartes, voir `SPREADS` dans `app.js`) :
1. reconstruit le prompt exact (tarologue professionnel, format JSON strict, tient compte des positions si fournies),
2. appelle l'API Anthropic avec la clé stockée dans la variable d'environnement **`ANTHROPIC_API_KEY`** (jamais exposée au navigateur),
3. renvoie `{cards: [...], synthesis}` au client (un texte par carte, dans le même ordre, quel que soit le nombre de cartes du tirage).

Si l'appel échoue ou dépasse son délai (20 à 45 secondes selon le nombre de cartes du tirage — `generateAIReading()` dans `app.js`, le même principe que `max_tokens` côté serveur : plus il y a de cartes, plus l'IA a de texte à rédiger, plus il lui faut de temps), l'app bascule automatiquement sur un texte généré localement (`synthesisParagraphs`/`synthesisParagraphsGeneric` selon le tirage, `interpretationFor`) — l'utilisateur n'est jamais bloqué. Ce repli reste silencieux à l'écran (juste une petite note), mais la cause exacte (délai dépassé, erreur HTTP, réponse invalide) est journalisée dans la console du navigateur pour le diagnostic.

### Protéger l'usage IA (recommandé tant que l'appli est personnelle)
Coût réel : de l'ordre du centime par tirage, variable selon le nombre de cartes (facturation à l'usage sur console.anthropic.com, indépendante d'un éventuel abonnement Claude.ai — les deux sont des produits distincts ; les grands tirages comme la Croix celtique ou l'Année à venir coûtent proportionnellement plus qu'un tirage à 1 ou 3 cartes). Le portrait de personnalité (`/api/portrait`), les textes astraux personnalisés (`/api/astral-text`) et la rétrospective annuelle (`/api/retrospective`) ajoutent chacun un appel comparable, mais respectivement une seule fois par profil, une seule fois par profil et une seule fois par an (mis en cache ensuite). Le texte enrichi de la comparaison de thèmes (`/api/comparison-text`) suit la même logique, une seule fois **par proche** (pas par profil) tant que ses informations de naissance ne changent pas. L'Horoscope du jour (`/api/ritual`) est en revanche **récurrent** : un petit appel supplémentaire chaque jour, du même ordre qu'un tirage à 1 carte. Pour éviter que quelqu'un d'autre qui tomberait sur l'URL de l'appli déclenche des appels avec ta clé :
- Définir une variable d'environnement **`APP_ACCESS_CODE`** (n'importe quelle chaîne secrète). Tant qu'elle est définie, le backend refuse toute requête qui ne fournit pas ce même code — l'appli le demande une fois côté client et le mémorise.
- Recommandé en complément, quel que soit l'usage : fixer un **plafond de dépense mensuel strict** sur console.anthropic.com (Settings → Limits) pour ne jamais pouvoir dépasser un montant que tu choisis.
- Pour ouvrir l'appli à d'autres plus tard : supprimer `APP_ACCESS_CODE` sur Vercel — aucun changement de code nécessaire. Penser alors à revoir le plafond de dépense en conséquence.

## Profil astral — comment ça marche
`POST /api/astral` (`api/astral.js`) calcule un thème astral complet à partir d'une date, heure et lieu de naissance. Reçoit `{ date: "AAAA-MM-JJ", time: "HH:MM" | null, place: string }` (heure **locale** au lieu de naissance ; `time: null` pour une heure de naissance inconnue — voir plus bas) et renvoie :
```json
{
  "resolvedPlace": "Lyon, Rhône-Alpes, France",
  "latitude": 45.75, "longitude": 4.85,
  "timezone": "Europe/Paris",
  "utcInstant": "1990-07-15T12:00:00.000Z",
  "timeUnknown": false,
  "sunSign": "Cancer", "moonSign": "Bélier",
  "ascendant": { "longitude": 201.02, "sign": "Balance", "degreeInSign": 21.02 },
  "midheaven": { "longitude": 115.94, "sign": "Cancer", "degreeInSign": 25.94 },
  "houseSystem": "placidus",
  "houseCusps": [{ "house": 1, "longitude": 201.02 }, "... x12"],
  "houseWarning": null,
  "bodies": {
    "sun": { "longitude": 112.75, "sign": "Cancer", "degreeInSign": 22.75, "house": 9, "retrograde": false },
    "moon": { "...": "..." },
    "mercury": {}, "venus": {}, "mars": {}, "jupiter": {}, "saturn": {}, "uranus": {}, "neptune": {}, "pluto": {}
  },
  "aspects": [{ "bodies": ["sun", "jupiter"], "type": "conjonction", "angle": 0, "orb": 0.2 }, "..."]
}
```
Pipeline en 5 étapes, chacune sur un service/bibliothèque activement maintenu (ou sur des formules maison, pour les étapes 4-5) :
1. **Géocodage** — [Open-Meteo Geocoding API](https://open-meteo.com/en/docs/geocoding-api) (gratuite, sans clé) : convertit le lieu en latitude/longitude, et renvoie directement le **fuseau IANA** du lieu (ex. `"Europe/Paris"`) via GeoNames.
2. **Heure UTC exacte** — [Luxon](https://moment.github.io/luxon/) convertit l'heure locale dans ce fuseau, en tenant compte des règles historiques de changement d'heure (base IANA intégrée à Node). Un contrôle maison détecte les heures locales qui n'ont jamais existé (le "trou" d'un passage à l'heure d'été) et renvoie une erreur claire plutôt que de laisser Luxon deviner silencieusement.
3. **Positions planétaires** — [astronomy-engine](https://github.com/cosinekitty/astronomy) calcule la longitude écliptique géocentrique "de la date" de chaque corps (Soleil à Pluton), d'où sont dérivés signe zodiacal, degré dans le signe et rétrogradation.
4. **Maisons (Placidus) + Ascendant/MC** — calculés à la main par-dessus l'obliquité de l'écliptique et le temps sidéral local que fournit déjà astronomy-engine (pas de dépendance supplémentaire). Algorithme porté d'une implémentation vérifiée contre `swe_houses` (Swiss Ephemeris) à ~1.5' près par la communauté d'astronomy-engine ([discussion #391](https://github.com/cosinekitty/astronomy/discussions/391)). Le système Placidus devient peu fiable au-delà d'environ 66,5° de latitude (cercles polaires) : `houseWarning` le signale dans la réponse plutôt que de renvoyer un résultat silencieusement dégradé.
5. **Aspects** — conjonction, sextile, carré, trigone, opposition entre chaque paire de corps, avec un orbe de 6 à 8° selon le type.

**Heure de naissance inconnue** : envoyer `time: null` fait calculer le thème à midi local (convention standard) ; `timeUnknown: true` et `ascendant`/`midheaven`/`houseCusps`/`houseWarning`/`bodies.*.house` valent `null` dans la réponse (une heure précise est indispensable pour ces calculs-là), mais signes et aspects restent fiables et sont toujours renvoyés.

**Vie privée** : la date/heure/lieu de naissance ne sont utilisées que le temps du calcul (fonction serverless sans état, rien n'est journalisé ni persisté côté serveur) — c'est au client de les garder en `localStorage` s'il veut les réutiliser. Même protection optionnelle `APP_ACCESS_CODE` que `/api/reading` (en-tête `X-App-Access-Code`).

### Client : onglet Profil
Barre du bas → **Profil** → une tuile par section : **Profil astral**, **Journal** (l'ancien onglet Journal a fusionné ici), **Statistiques**, **Mes proches** (voir plus bas), et une **Rétrospective** annuelle quand elle est prête. Première visite de « Profil astral » : formulaire (prénom, **genre**, date/heure/lieu de naissance, case « heure inconnue ») → appel à `/api/astral` → tout le résultat mis en cache dans `localStorage` (`delphesProfile`, jamais renvoyé au serveur ensuite) ; les visites suivantes affichent directement le résultat, avec un bouton « Modifier mes informations » qui rouvre le formulaire prérempli.

**Genre** (champ optionnel du formulaire, « Féminin » / « Masculin » / « Préfère ne pas préciser » — ce dernier par défaut) : sert uniquement à accorder correctement les textes rédigés par l'IA (portrait, textes astraux, comparaison de thèmes), jamais à autre chose. Retour direct d'utilisatrice ("il faut penser à mettre le sexe... pour que le texte soit généré avec le bon genre"). Transmis tel quel dans `profileForPortrait()`/`profileForAstralText()` (`gender: "f" | "m" | null`) et dans `profileForComparisonText()` (`yourGender`/`theirGender`, chacun indépendant). Côté serveur, chaque endpoint IA accorde explicitement le texte au genre connu ; quand il n'est pas précisé, le prompt demande explicitement une formulation neutre (déjà le comportement par défaut avant l'ajout de ce champ — aucune régression pour un profil existant qui ne le renseigne pas). Dans `api/comparison-text.js`, `genderNote()` gère les deux personnes indépendamment : le genre de l'une peut être connu sans que celui de l'autre le soit — la règle "jamais de pronom genré" ne s'assouplit que pour la personne dont le genre est effectivement connu. Le même champ existe sur chaque proche (« Mes proches », voir plus bas) ; `comparisonFingerprint()` inclut désormais aussi le genre des deux thèmes, pour que le texte de comparaison en cache se régénère automatiquement si l'un des deux genres est renseigné ou modifié après coup.

Le résultat n'est pas qu'une liste brute de signes et degrés : `natalSummaryParagraph()` ouvre l'écran par un paragraphe récapitulatif (Soleil/Lune/Ascendant + densité des aspects), et chaque planète, l'Ascendant et chaque aspect ont 1-2 phrases d'explication (`natalPlanetSentence()`/`natalAscendantSentence()`/`natalAspectSentence()`) — composées à partir d'un vocabulaire réutilisable (`PLANET_THEMES` : le domaine de vie de chaque planète ; `signQuality()` : le mot-clé du signe, via `ZODIAC_MAJOR_LINKS`, la même table que pour « Apprendre »). Entièrement local, aucun appel IA — c'est le texte affiché tant que `/api/astral-text` (voir plus bas) n'a pas encore répondu, ou en repli s'il échoue.

Le prénom reçoit en plus une **numérologie** (`nameNumerology()` dans `app.js`, méthode pythagoricienne classique réduite à 1-9, volontairement sans nombre maître 11/22/33) dont la signification réutilise directement `NUMBER_KEYS`, la même grammaire symbolique que les cartes numérales.

Contrairement au nombre du prénom (fixe à vie), trois nombres évoluent avec le temps — la **numérologie du temps** (`personalYearNumber()`/`personalMonthNumber()`/`personalDayNumber()`, formule classique jour+mois de naissance+année en cours [+mois en cours [+jour en cours]], même réduction 1-9) : l'année personnelle change chaque 1er janvier, le mois personnel chaque mois, le jour personnel chaque jour. Les deux premiers sont affichés dans l'écran Profil astral juste sous le nombre du prénom ; le jour personnel, lui, alimente uniquement l'Horoscope du jour (voir plus bas), où sa granularité quotidienne compte davantage qu'un affichage statique.

Quand un profil est enregistré, `generateAIReading()` envoie automatiquement un résumé (`profileForReading()` : prénom, nombre numérologique, signes solaire/lunaire/ascendant, année personnelle) à `/api/reading`, qui l'intègre avec subtilité à la lecture si c'est pertinent — sans jamais devenir un horoscope générique ni éclipser les cartes tirées. Sans profil enregistré, la lecture se comporte exactement comme avant.

**Divinité tutélaire** : `tutelaryDeity()` détermine la figure mythologique la plus représentée dans le thème natal — chaque planète « vote », avec un poids plus fort pour les planètes personnelles (Soleil, Lune, Ascendant, Mercure, Vénus, Mars) que pour Jupiter/Saturne, et en excluant Uranus/Neptune/Pluton — trop lentes pour différencier un individu d'une génération entière. Le vote se fait à la précision maximale que l'illustration du jeu permet à ce jour : d'abord le **décan exact** du signe (tranche de 10°, `DECAN_MINOR_CARDS`/`decanCardFor()` — tradition des "decanates" du Golden Dawn/Thoth Tarot, chaque signe divisé en 3 décans pointant chacun vers une carte numérale 2-10 d'une enseigne selon sa triplicité élémentaire) ; si cette carte a déjà sa propre figure illustrée (`NUMBER_CARD_DEITY` — Épées et Bâtons complets, plus l'As à 5 de Coupes, donc 7 signes sur 12 pleinement couverts : Bélier/Lion/Sagittaire, Balance/Verseau/Gémeaux et désormais Cancer ; Scorpion n'a lui que son 1er décan couvert, 5 de Coupes = Orphée), le vote va à cette figure précise, piochée dans l'ensemble de la bibliothèque (~70 figures) plutôt que dans les seules 12 divinités des majeurs ; sinon (Coupes 6-10 et Deniers, pas encore illustrées), repli sur le dieu du majeur associé au signe entier via `ZODIAC_MAJOR_LINKS`, comme avant cette extension — et donc de plus en plus rare au fur et à mesure que ces enseignes seront illustrées. Affichée sous forme de carte cliquable (glyphe + nom + note), qui renvoie vers la fiche complète de la divinité, avec une explication de ce choix (voir `/api/astral-text` juste en dessous : `tutelaryReason` en IA, ou une phrase de repli qui énumère les placements les plus lourds via `tutelaryReasonFallback()`).

**Portrait de personnalité** (`POST /api/portrait`, `api/portrait.js`) : un texte suivi de 3-4 paragraphes, rédigé par l'IA à partir d'un résumé du thème (signes, numérologie, divinité tutélaire, aspects les plus serrés — jamais le thème natal complet), sans jargon technique ("aspect", "orbe"…) traduit en traits de caractère concrets. Généré **une seule fois** et mis en cache dans le profil (`profile.portrait`), jamais régénéré tant que les informations de naissance ne changent pas — voir `ensurePortrait()` dans `app.js`, même mécanique de discrétion qu'`ensureTransits()` (aucun appel avant qu'un code d'accès existe déjà). Remplace le paragraphe récapitulatif local (`natalSummaryParagraph()`) une fois prêt ; celui-ci reste affiché en attendant ou si l'appel échoue.

**Textes astraux personnalisés** (`POST /api/astral-text`, `api/astral-text.js`) : à la différence du portrait (un texte d'ensemble), une phrase distincte générée par l'IA pour *chaque* case — le nombre du prénom, chaque planète, l'ascendant, chaque aspect (plafonné aux 10 aspects les plus exacts par orbe) — plus l'explication de la divinité tutélaire. `profileForAstralText()` construit le résumé envoyé (mêmes principes de sobriété que pour le portrait), avec une clé stable par aspect (`sun_carré_moon`, etc., voir le commentaire dans `app.js`) pour que le texte retrouve la bonne case quel que soit l'ordre. Générées **une seule fois** et mises en cache dans le profil (`profile.astralText`), régénérées si les informations de naissance changent (même mécanique que `ensurePortrait()`) **ou** si la divinité tutélaire recalculée en direct ne correspond plus à celle pour laquelle le cache a été écrit (`astralText.tutelaryDeityKey`, comparé dans `ensureAstralText()`) — ce second cas couvre à la fois les profils enregistrés avant l'extension aux décans ci-dessus et, plus tard, l'illustration de Coupes/Deniers qui affinera le calcul pour d'autres personnes : sans ce garde-fou, `tutelaryReason` continuerait de justifier une figure différente de celle réellement affichée. Tant qu'un champ précis n'est pas encore généré (ou en cas d'échec), `renderProfilResults()` retombe silencieusement sur la phrase locale correspondante (`natalPlanetSentence()` etc.) — jamais de case vide.

**Animal représentatif** (fonctionnalité "premium") : `representativeAnimal()` détermine un animal symbolique (catégorie "Animaux" de `SYMBOL_LIBRARY`) à partir de deux signaux — le signe solaire du thème natal (`SIGN_ANIMAL`, un animal par signe, choisi pour son lien mythologique déjà écrit dans la fiche du symbole quand il existe, sinon un lien thématique/iconographique) et, une fois assez de tirages enregistrés pour dégager un vrai motif, le domaine de question le plus fréquent du Journal (`DOMAIN_ANIMAL`, sur les mêmes 6 domaines que `QUESTION_DOMAINS`/`detectDomain()`, via `journalTrends().topDomain`) — ce second signal prime sur le premier quand il tranche, le thème astral servant de repli tant qu'aucun sujet ne se dégage clairement. Se débloque après `REPRESENTATIVE_ANIMAL_MIN_READINGS` (10) tirages enregistrés **et** l'activation du mode premium — un simple interrupteur local (`isPremiumEnabled()`/`setPremiumEnabled()`, clé `delphesPremium` dans `localStorage`, visible dans l'écran Profil astral) : un aperçu d'un futur vrai palier payant, sans aucune infrastructure de compte ni de paiement réelle (l'app reste 100% locale — voir « Pistes de suite possibles » plus bas). Explication toujours locale/déterministe, sans appel IA, volontairement plus légère que la divinité tutélaire.

**Comparaison de thèmes — « Mes proches »** (tuile de l'onglet Profil, `showRelations()`) : le même principe que la synastrie en astrologie traditionnelle (croiser deux thèmes plutôt qu'en lire un seul), volontairement généralisé à toute relation — partenaire, enfant, parent, fratrie, ami·e — plutôt que réservé au couple. Chaque proche (`delphesRelations` dans `localStorage`, jamais envoyé au serveur au-delà du calcul du thème via `/api/astral`, exactement comme le profil principal) a son propre thème complet, géré indépendamment (ajout/modification/suppression, `showRelationForm()`) — cette gestion reste **toujours gratuite**, ce n'est que de la donnée, pas de l'interprétation. `compareProfiles()`, entièrement déterministe et local (aucun appel IA), croise ensuite les deux thèmes :
- **Élément dominant** (`SIGN_ELEMENT`, dérivé de la même triplicité que `DECAN_MINOR_CARDS` — pas une nouvelle classification) : même élément = résonance, éléments complémentaires (Feu/Air, Terre/Eau) = équilibre naturel, éléments opposés = tension à apprivoiser plutôt qu'un problème en soi (`elementDynamic()`).
- **Divinité tutélaire commune**, quand `tutelaryDeity()` calculé séparément pour chaque thème tombe sur la même figure.
- **Points communs et points de tension potentiels** (`synastryAspects()`) : Soleil/Lune/Ascendant/Vénus/Mars de chacun comparés deux à deux avec `findAspect()` — les mêmes types et orbes que `CLIENT_ASPECTS` (déjà utilisés pour les aspects natals et pour `strongestTransitAspect()`), ici appliqués entre deux personnes plutôt qu'au sein d'un seul thème ; conjonction/trigone/sextile classés comme points communs, carré/opposition comme tensions potentielles — jamais présentées comme des incompatibilités. Vénus (affinités, valeurs) et Mars (énergie, façon d'agir) sont venus compléter Soleil/Lune/Ascendant après un retour direct ("tu ferais quoi pour pousser encore cette fonction ?") — jusqu'à 5 points par thème, donc jusqu'à 5×5 combinaisons possibles, les 5 plus exacts remontant dans chaque catégorie (common/tense).

Chaque proche déjà enregistré peut être modifié (pas seulement supprimé) depuis « Mes proches » ou directement depuis l'écran de comparaison (`showRelationForm(id)`, préexistant côté logique mais qu'aucun bouton n'exposait avant un retour direct). Le formulaire d'un proche a le même champ **Genre** optionnel que le profil principal (voir plus haut) — sert au même usage, pour que le texte enrichi par IA de la comparaison (plus bas) accorde correctement ce qui concerne le proche.

Pour qu'une lecture répétée ne sonne pas comme un même gabarit recopié pour tout le monde, `elementDynamic()` et `synastryAspects()` piochent chacun parmi plusieurs formulations par cas (`ELEMENT_DYNAMIC_VARIANTS`, `SYNASTRY_ASPECT_VARIANTS`, au moins 3 variantes chacune, plus explicatives que la version initiale — 1 à 2 phrases par variante plutôt qu'un simple fragment). Le choix n'est pas aléatoire : `stableVariant()` (hash djb2) dérive une variante stable à partir de la paire de signes exacte en jeu (12×12 combinaisons pour l'élément, signe+point+type d'aspect pour la comparaison) — une même comparaison affiche donc toujours le même texte d'un rendu à l'autre (pas de scintillement au changement d'écran), tout en donnant à des comparaisons différentes de bonnes chances de tomber sur des formulations différentes. Grammaire : le côté "toi" utilise des groupes nominaux correctement accordés (`SYNASTRY_POINT_YOUR` : "Ta Lune", pas "Ton Lune") et le côté "proche" nomme la personne plutôt que d'utiliser un pronom genré ("la Lune de Léa", jamais "sa Lune").

**Texte enrichi par IA** (`POST /api/comparison-text`, `api/comparison-text.js`) : bonus optionnel au-dessus de la comparaison déterministe ci-dessus (qui reste entièrement fonctionnelle sans lui) — un texte suivi de 2-3 paragraphes qui tisse les résultats déjà calculés (élément, points communs/tensions, divinité commune) en une lecture fluide, avec un ton adapté au type de relation (`RELATION_TONE_HINT` côté serveur : jamais de vocabulaire de couple pour un parent/enfant/fratrie/ami·e, seulement pour un·e partenaire). `profileForComparisonText()` construit le résumé envoyé — jamais les deux thèmes complets, même sobriété que `profileForPortrait()`. Généré une seule fois par proche et mis en cache directement sur l'entrée du proche (`relation.comparisonText` dans `delphesRelations`), régénéré si l'empreinte des dates de naissance des deux thèmes concernés change (`comparisonFingerprint()`, même garde-fou que `astralText.tutelaryDeityKey`) — voir `ensureComparisonText()`, déclenchée uniquement en mode premium (même logique de discrétion qu'`ensurePortrait()` : jamais de prompt de code d'accès surprise, échec silencieux, un seul appel par proche tant qu'aucun texte n'est en cache).

**Fiabilité factuelle du texte généré** : retour direct d'utilisatrice — un texte généré affirmait qu'un fils avait "une Lune en Poissons" alors que c'était son Soleil (sa Lune était en Cancer), malgré des données d'entrée correctes : l'IA avait interverti deux placements en rédigeant. Le prompt de `api/comparison-text.js` présente désormais les données en un **bloc par personne** (`personBlock()` : "Thème de Sophie :" / "Thème de Léa :", chacun listant seulement ses propres placements) plutôt qu'une ligne par planète mélangeant les deux prénoms sur la même ligne — plus explicite pour l'IA — et une consigne d'exactitude explicite ("EXACTITUDE AVANT TOUT… ne les mélange jamais entre les deux personnes… n'invente jamais un placement qui n'est pas listé"). `api/portrait.js` et `api/astral-text.js` reçoivent une consigne équivalente en prévention (même risque de confusion Soleil/Lune en rédigeant, même sans deuxième personne à mélanger). Cela réduit fortement le risque sans pouvoir l'éliminer complètement — une IA générative reste capable d'erreurs occasionnelles même avec des données correctes en entrée ; en cas de doute, les données brutes affichées ailleurs dans l'app (signes, degrés) font foi.

**Comparaison de groupe** (bouton « 👪 Comparer plusieurs proches » dans « Mes proches », visible dès 2 proches enregistrés) : étend la comparaison à deux à un groupe entier — toi et plusieurs proches sélectionnés à la fois, pour voir la dynamique de toute une famille en un coup d'œil plutôt que d'ouvrir une comparaison à la fois. `compareGroup(people)` calcule `compareProfiles()` pour **chaque paire possible** au sein du groupe (C(n,2) paires, pas seulement toi vis-à-vis de chacun — donc aussi, par exemple, deux enfants entre eux) ; volontairement pas de "score de groupe" unique : une famille n'est pas une seule compatibilité mais un réseau de relations à deux qui s'additionnent. Vue condensée par paire (élément dominant, divinité commune, aspect le plus exact) — pour les paires qui ne t'incluent pas, l'aspect est présenté factuellement (type + signes) plutôt qu'avec la phrase personnalisée de `synastryAspects()`, écrite pour s'adresser à toi spécifiquement et donc incorrecte pour une paire entre deux proches. Même découpage gratuit/premium que la comparaison à deux : sélection des proches toujours gratuite, dynamique de groupe elle-même premium.

Fonctionnalité premium (voir plus bas) : le recueil et la gestion des proches restent gratuits, mais la comparaison interprétée elle-même (à deux comme en groupe) est cadenassée sans le mode premium — seuls les signes bruts des deux thèmes restent visibles en aperçu pour une comparaison à deux.

### Découpage gratuit / premium

Toujours porté par le même interrupteur local `isPremiumEnabled()` (rien de tel qu'un vrai paiement — voir « Pistes de suite possibles »), mais depuis cette étape le découpage couvre l'app entière, en vue d'une future publication App Store avec un vrai palier payant (StoreKit). Défini explicitement avec l'utilisatrice ; répertorié ici pour qu'un futur changement de contenu (nouvelle carte, nouveau symbole…) sache dans quel panier tomber par défaut.

**Important — défaut actuel** : `isPremiumEnabled()` renvoie `true` tant qu'aucune valeur n'est stockée (`localStorage.getItem("delphesPremium") !== "0"`), donc **tout le monde a l'accès complet par défaut**, y compris les personnes qui testaient déjà l'app avant l'introduction de ce découpage — aucune manip de leur part. Seul un choix explicite (décocher la case dans l'écran Profil astral, qui écrit `"0"`) fait basculer un appareil en expérience gratuite ; c'est volontairement l'inverse d'un vrai lancement payant. Au moment du vrai lancement App Store, ce défaut devra être inversé (`localStorage.getItem("delphesPremium") === "1"`) pour que le mode gratuit redevienne l'état de repli normal — voir « Pistes de suite possibles ».

- **Toujours gratuit, sans interrupteur** : 1 tirage général par jour (`FREE_SPREAD_TYPES`, `canStartSpread()`, `hasUsedFreeGeneralReadingToday()`/`markFreeGeneralReadingUsed()`, reset à minuit via une simple comparaison de date) ; la carte du jour ; le Journal et ses statistiques ; les données brutes du Profil astral (signes, degrés, maisons — tout sauf les phrases d'interprétation, voir plus bas) ; la « Lecture traditionnelle » (Marseille) de chaque carte, jamais gatée.
- **Gratuit, sous-ensemble figé (les *n* premiers dans l'ordre alphabétique d'affichage)** : les 2 premiers arcanes majeurs (`FREE_MAJORS` : Le Mat, I — Le Bateleur), les 4 figures de cour Rois (`FREE_COURTS` : un Roi par enseigne), les 5 premiers symboles de la bibliothèque (`FREE_SYMBOLS`, tri alphabétique `localeCompare(…,"fr")` sur `SYMBOL_LIBRARY[id].label`), les 4 premières figures mythologiques (`FREE_FIGURES`, même tri sur les clés de `DEITY_NOTES`) — `isCardMythFree()`/`isSymbolLoreFree()`/`isFigureLoreFree()` testent l'appartenance à ces ensembles. Les cartes numérales n'ont **jamais** d'éclairage mythologique gratuit (règle explicite, aucune exception).
- **Toujours premium** : tous les autres tirages (Oui/Non, Amour, Croix celtique, Année à venir) ; l'« Éclairage mythologique » des cartes hors des sous-ensembles ci-dessus ; le texte « Aux origines du symbole » et « Le mythe » hors des 5/4 premiers ; dans le Profil astral, le portrait de personnalité, le résumé du thème, la divinité tutélaire et l'animal représentatif en entier (section toujours visible mais cadenassée), et toute phrase d'interprétation (nombre du prénom, année/mois personnels, planètes, ascendant, aspects) — les libellés et valeurs brutes restant affichés, seule la phrase explicative est masquée ; la comparaison de thèmes interprétée dans « Mes proches », à deux comme en groupe (élément dominant, points communs/tensions, divinité tutélaire commune, texte enrichi par IA — la gestion des proches elle-même reste gratuite, voir plus haut).

Mécanique commune : `premiumLockHTML(message)` rend un bloc 🔒 réutilisable partout où du contenu est masqué ; dans `renderProfilResults()`, un raccourci local `expl(text)` centralise le masquage des phrases d'interprétation (`premiumOn ? texte : ""`) pour ne pas répéter la condition à chaque case. Les sections « Figures liées »/« Cartes concernées » d'un symbole ou d'une figure restent toujours visibles même verrouillé — considérées comme de la navigation, pas de l'« explication ». Pour éviter de gaspiller des appels IA payants sur du contenu qu'un profil gratuit ne verra jamais, `ensurePortrait()`/`ensureAstralText()` ne sont plus appelées (ni depuis `home()`, ni depuis `showProfilAstral()`) tant que `isPremiumEnabled()` est faux.

### Horoscope du jour — comment ça marche
Affiché côté interface sous le titre « Horoscope du jour » ; en interne (fonctions, clé `localStorage`, endpoint `/api/ritual`), le nom garde le préfixe historique `ritual` — pas de renommage en profondeur pour un changement de libellé visible.

`POST /api/transits` (`api/transits.js`) calcule les positions planétaires **du jour** (Soleil à Pluton), sans recevoir aucune donnée personnelle — le résultat est identique pour tout le monde, seul l'instant de la requête compte. Le client (`ensureTransits()` dans `app.js`) met ce résultat en cache un jour entier dans `localStorage` (`delphesTransits`) et ne rappelle l'endpoint qu'une fois par jour.

`strongestTransitAspect()` compare ensuite, entièrement côté client, ces positions du jour au thème natal du Profil astral (déjà en `localStorage`, jamais renvoyé au serveur pour ce calcul) : l'aspect le plus exact entre les planètes rapides du jour (Soleil, Lune, Mercure, Vénus, Mars) et les points natals (Soleil, Lune, Ascendant), avec les mêmes types/orbes que `/api/astral`. Gratuit et instantané (aucun appel IA pour ce calcul) — son résultat, ainsi que les signes du Soleil et de la Lune du jour, alimente `ritualSummary()`, envoyé à `/api/ritual` juste en dessous. Une ancienne section « Horoscope du jour » affichait ces mêmes signes séparément, en plus du rituel : supprimée (elle faisait doublon), sa matière a d'abord été entièrement absorbée dans la recommandation unifiée — avant que son titre d'origine ne lui soit rendu par la suite (voir le paragraphe suivant).

`POST /api/ritual` (`api/ritual.js`) fusionne carte du jour, transits du jour (signes + aspect le plus marqué), **thème natal fixe** (Soleil/Lune/ascendant de naissance) et **nombre personnel du jour** (`personalDayNumber()`, pas du mois) en une seule recommandation concrète, plutôt que des blocs séparés à interpréter soi-même. Le thème natal fixe et le nombre du jour ont été ajoutés après un retour direct : sans eux, deux jours qui partagent la même carte (le cycle ne compte que 22 majeurs, voir `dayOfYear()`) et le même signe solaire transitant (constant tout un mois) produisaient un texte quasi identique — le thème natal distingue une personne d'une autre même à carte/signe du jour identiques, et le nombre personnel change chaque jour (contrairement au mois personnel). Le prompt sépare explicitement dans son texte ce qui est fixe (thème natal) de ce qui varie aujourd'hui, et demande explicitement à l'IA d'éviter toute formule interchangeable d'un jour ou d'une personne à l'autre. Contrairement au portrait et à la rétrospective (générés une fois), rappelé **une fois par jour** — coût récurrent, du même ordre qu'une lecture à 1 carte — et mis en cache dans `localStorage` (`delphesRitual`) le temps de la journée. N'apparaît sur l'accueil que si un Profil astral est enregistré, et jamais via un prompt intrusif : le premier appel n'est déclenché que si le code d'accès a déjà été mémorisé par ailleurs (ce qui est garanti dès qu'un Profil astral existe).

### Journal intelligent — comment ça marche
`journalTrends()` dans `app.js` analyse le Journal (à partir de 3 tirages enregistrés, pour éviter qu'un seul tirage ne « devienne » une tendance) et dégage la carte la plus fréquente et le thème de question le plus fréquent (via `detectDomain()`, déjà utilisé pour la synthèse locale). Affiché en tête du Journal (« Tes tendances »), et envoyé en résumé minimal (`journalTrendsForReading()`) à `/api/reading` pour que la lecture IA puisse, avec beaucoup de subtilité, en tenir compte — jamais au détriment des cartes tirées ce jour-là.

**Affinités mythologiques** (dans Statistiques) : contrairement aux autres fonctionnalités de personnalisation (calculées une fois pour toutes à partir du thème astral), celle-ci se construit et s'affine à mesure que le Journal grossit. `journalStats()` dépouille chaque carte de chaque tirage enregistré et compte, sur l'ensemble du Journal, les divinités (`cardDeityLabel()`, la même fonction que les fiches détail, donc une carte numérale ne compte que si elle a sa propre figure via `NUMBER_CARD_DEITY`) et les symboles (`c[5]`, le même champ qui alimente « Cartes concernées ») qui reviennent le plus souvent — les 5 premiers de chaque, cliquables vers leur fiche complète. Toujours gratuit (fait partie de « le Journal et ses statistiques », jamais gaté par le découpage premium — voir plus haut) et purement local, aucun appel IA.

### Mémoire du Journal — comment ça marche
Contrairement à `journalTrends()` (une tendance globale), `cardMemory()` est un rappel ponctuel propre à chaque tirage : si l'une des cartes tirées aujourd'hui est déjà apparue dans un tirage précédent sur un sujet proche (même domaine détecté par `detectDomain()`), le tirage précédent le plus récent est envoyé à `/api/reading` (`{cardName, date, domainLabel}` — jamais le texte de la question passée) pour que la lecture IA puisse, si c'est pertinent, le mentionner brièvement.

### Rétrospective annuelle — comment ça marche
`POST /api/retrospective` (`api/retrospective.js`) rédige un bilan de l'année écoulée, une fois par an, à l'anniversaire de naissance (repère plus intuitif qu'un 1er janvier arbitraire pour « une année de ta vie »). `ensureRetrospective()` scope le Journal aux 12 derniers mois (`journalStatsSince()`, en s'appuyant sur `journalStats()` généralisé à un sous-ensemble d'entrées), exige au moins 3 tirages sur la période (comme `journalTrends()`), puis envoie un résumé agrégé — jamais le texte des questions ni des notes — à l'API. Le résultat est mis en cache dans `localStorage` (`delphesRetrospective`, avec l'année de génération) et surfacé dans l'onglet Profil sous forme de 4e tuile (à côté de Profil astral, Journal et Statistiques) tant que l'année en cours correspond ; une nouvelle rétrospective n'est générée qu'au prochain anniversaire.

## Déployer sur Vercel

Vercel héberge en un seul projet le site statique (racine du repo) et la fonction backend (`api/reading.js`) — c'est l'option la plus simple pour ce projet.

1. Créer une clé API sur [console.anthropic.com](https://console.anthropic.com) (nécessite un moyen de paiement configuré) et, si souhaité, y fixer un plafond de dépense mensuel (Settings → Limits).
2. Sur [vercel.com](https://vercel.com), **New Project** → importer ce dépôt GitHub.
3. Aucune configuration de build n'est nécessaire (site statique + dossier `api/` détectés automatiquement).
4. Dans **Settings → Environment Variables**, ajouter :
   - `ANTHROPIC_API_KEY` = la clé créée à l'étape 1 (cocher Production, Preview et Development).
   - `APP_ACCESS_CODE` = un code secret de ton choix (voir ci-dessus ; optionnel mais recommandé tant que l'appli est personnelle).
5. Déployer. Vercel donne une URL du type `https://ton-projet.vercel.app/`.

Pour tester en local avec la CLI Vercel :
```bash
npm install
cp .env.example .env   # puis renseigner ANTHROPIC_API_KEY (et APP_ACCESS_CODE si souhaité)
npx vercel dev
```

*(Netlify fonctionne aussi selon un principe identique : Netlify Functions à la place du dossier `api/`, et la même variable d'environnement dans Site settings → Environment variables — mais nécessiterait d'adapter `api/reading.js` au format Netlify Functions.)*

## Installer sur iPhone une fois déployé
1. Ouvrir l'URL de déploiement (Vercel) dans Safari sur l'iPhone.
2. Appuyer sur Partager → Ajouter à l'écran d'accueil → Ajouter.
3. L'application apparaît avec son icône et s'ouvre comme une app, y compris hors ligne (sauf la lecture IA, qui a besoin du réseau — avec repli automatique sinon).
